# ADR-0003：事件的执行提示字段与封闭的复核决定

- **状态**：已接受（实施用）
- **日期**：2026-10-28
- **影响文件**：`contracts/contracts/events.py`、`contracts/contracts/enums.py`、`docs/implementation/30-backend.md`

## 背景

运行时上报的 `VisionEvent` 只描述观察，不决定执行归属；归属由后端解析器判定（基线 §7）。但存在两类必须显式指定执行的场景：

1. 隔离事件改绑（`POST /events/{event_id}/assign`）：操作者已选定执行，解析器不应再猜；
2. 回溯重放或测试：同一事件需要落到指定执行。

此外，人工复核只有两种业务结论可用——确认步骤完成、确认步骤失败。基线要求复核记录操作者、决定、理由与证据（§13.3），但没有定义“决定”的取值集合；若允许自由文本，审计与前端会漂移。

## 决定

1. `VisionEvent.execution_id: str | None = None` 是可选的**提示**。存在时解析器必须校验工位、执行状态、相机绑定与时间窗，校验失败仍按隔离处理，绝不因为字段存在就跳过校验。
2. `RoutedSOPEvent` 重新声明 `execution_id: str`（必填），解析后的路由事件永远携带确定的执行。
3. 复核决定为封闭集合 `ReviewDecision = {MARK_COMPLETED, MARK_FAILED}`。复核请求必须带非空 `operator` 与 `reason`，可带步骤匹配事件的 `AVAILABLE` 证据 ID。
4. 不引入 `pass`/`fail`、置信度或“通过率”语义；`MARK_FAILED` 不等于视觉判断失败，只是人工结论。

## 理由

- 在事件上加可选字段保持运行时契约不变，解析器仍是唯一权威；改绑复用同一条解析与校验路径。
- 封闭决定集合让审计、告警与 UI 使用同一词汇；操作者和理由让任何人工状态变更可追溯。

## 什么会改变这个决定

- 解析元数据膨胀到无法塞进事件对象时，改为独立的路由包装（`RoutedEvent { event, resolution }`）；
- 出现第三种业务结论（如“返工后重试”）时，先补枚举值与测试，再改 API；
- 接入认证后，`operator` 由凭据派生，不再由调用方传入，但理由与证据仍必填。

## 后果

- 运行时发送 `execution_id` 是可选的；后端不得默认填充伪造执行。
- 前端复核表单不预选决定，且在状态已变化时返回 409 并要求刷新。
